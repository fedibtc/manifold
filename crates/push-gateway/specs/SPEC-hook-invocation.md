# SPEC-hook-invocation: durable bearer-capability hook delivery

## Record justification

The invocation contract binds external hook callers, the mobile app's
notification handling, storage/outbox semantics, and the FCM provider
boundary, so no single implementation artifact can own it coherently.

## Bearer capability shape

Public hook invocation is `POST /hooks/{hook_id}/{hook_secret}`: a
non-secret public hook id plus a separate opaque bearer secret, authorized
by possession of the full URL with no Nostr auth. The secret is generated by
the gateway, returned only once in the create-hook response (marked
no-store/no-cache), and never stored in plaintext: invocation looks up by
`hook_id` and verifies a stored unique-indexed hash of the supplied secret
with constant-time comparison. The non-secret `hook_id` is
management/idempotency metadata for list/revoke, `notification_events`, and
outbox relations; current logging and metrics do not carry hook ids at all
([ARCH-push-gateway](./ARCH-push-gateway.md), observability).

## Accepted after durable enqueue

A new non-idempotent invocation verifies the hook secret and current policy,
then transactionally requires and snapshots at least one active non-stale target
before consuming any hook use/rate-limit counters or creating an event,
writes a `notification_events` row, and writes one `delivery_outbox` row per
target in one database transaction before returning `accepted` to the
caller. Provider delivery is never required for the HTTP response to
succeed.

Hook creation in every mode requires both a finite `policy.ttl_seconds` and an
`installation_id` that is currently registered, active, non-stale, and owned by
the authenticated recipient. This scopes FI formation completion to the
initiating installation.

If the named target is missing, disabled, or stale, invocation returns retryable
`503 target_installation_unavailable` without consuming hook counters, creating
an event, or pinning the caller's idempotency key. After signed refresh or
re-registration, retrying the same key may enqueue exactly once. An already
accepted retained event still replays its recorded target count even if the
installation later becomes ineligible.

The accepted delivery contract is ordinary best-effort provider transport:
`succeeded` means the configured provider accepted the request, not that the
device received or displayed it, the app handled it, or a person saw it. The
gateway has no app-receipt protocol. Each snapshotted target has the durable
five-minute terminal-resolution lifecycle in
[`SPEC-durable-state-lifecycle`](./SPEC-durable-state-lifecycle.md).

## Non-load-bearing workflow notifications

Notifications are advisory latency aids, not workflow acknowledgements. A
delayed or dropped device notification is expected behavior. It does not change
the target's provider-resolution outcome. The bounded target-resolution
lifecycle provides provider submission and actionable failure visibility instead
of device or application receipt.

[CLAIM-production-ready](../../../specs/CLAIM-production-ready.md) imports this
bounded best-effort provider-resolution property; it does not require device or
application receipt.

## App-open context ownership

Hook records own the mobile app-open contract: notification kind,
workflow/action, optional app deep link, open behavior, privacy posture, and
default display text. Invocation payloads are untrusted trigger data: they
may add an `idempotency_key` and constrained non-reserved reference data,
but cannot override visible title/body, notification identity, FCM routing
fields, or gateway-owned `pg.*` keys. The normalized notification snapshot
carries hook-owned routing hints as reserved `pg.*` data fields
(`pg.open_behavior`, `pg.privacy`, and optional `pg.workflow`, `pg.action`,
`pg.deep_link`); `privacy: "data_only"` suppresses title/body in the push
payload so sensitive workflows avoid placing details in notification display
text. Provider-specific background wake behavior is out of scope. The
worker and FCM provider pass the snapshot through unchanged.
FI formation uses a generic non-sensitive update notification. Its arrival is
not proof that DKG succeeded and carries no authoritative federation state; the
app reopens the durable formation driver and reconciles from its closest hard
state.

## Idempotent replay

If the caller supplies `idempotency_key`, `(hook_id, idempotency_key)` is
recorded as a compact accepted-key marker in the event/outbox transaction. The
hook secret must still match. Replay returns the recorded target count and does
not consume hook counters or create additional outbox rows, even if sensitive
event/outbox retention cleanup has run or max-use/rate-limit state has since
changed. Revocation or expiry terminates the bearer capability before replay
lookup, so a retained key does not authorize any response after either transition.
Markers remain through the finite hook lifetime plus a seven-day cleanup margin.
A new idempotency key is evaluated against current TTL, revocation,
max-use, rate-limit, and marker-capacity state. Calls without `idempotency_key`
are never deduplicated. FI formation creates its installation-scoped hook with an
exact 30-day TTL, covering DKG/wallet-service callback retry for that period.
This uses the single-process topology in
[`ARCH-push-gateway`](./ARCH-push-gateway.md), not a multi-replica coordination
design.

## Outbox rows and statuses

`notification_events` stores the accepted invocation and serialized
notification. `delivery_outbox` stores one row per target token snapshot:
recipient id, installation id, FCM token, platform, serialized notification,
status, attempt counters, retry time, and sanitized last error.
Worker-owned statuses:

- `pending` — durable row not yet attempted;
- `in_progress` — claimed by this process with a short lease in
  `next_attempt_at` and a `claim_id` fencing token;
- `retrying` — transient failure waiting for backoff;
- `succeeded` — provider accepted the delivery;
- `invalid_token` — provider classified the snapshotted token as permanently
  bad;
- `dead_letter` — transient failures exhausted the retry budget, the
  provider rejected the notification as a permanent non-token payload
  failure, the persisted serialized notification cannot be decoded, or the
  persisted five-minute resolution deadline elapsed.

Provider sends are at-least-once: a crash or lease expiry can retry an
`in_progress` row, and stale completions are fenced by `claim_id` so they
cannot overwrite a newer claim. Apps must tolerate duplicate push sends for
the same notification id.

Stored hook and outbox JSON is fail-closed. A hook row whose persisted
`data_json` cannot be decoded causes a sanitized internal error on the
request path — never treated as empty data. A claimed outbox row whose
`notification_json` cannot be decoded is terminally `dead_letter` with a
sanitized `last_error` and sanitized logs/metrics, never delivered via a
fallback notification.

## Provider delivery and invalid-token cleanup

Real FCM delivery is the opt-in `PUSH_GATEWAY_PROVIDER=fcm` mode; the
default provider is no-op/fake for local development, `defe`, and CI. The
`provider-fcm` crate owns the external Google boundary: service-account
credential parsing, OAuth2 JWT bearer assertions with access-token caching,
mapping gateway notifications to FCM HTTP v1 token messages, HTTP timeouts
and bounded concurrency, transport-agnostic outbound payload validation, and
provider response classification. The storage crate never depends on
provider errors; the server/worker translates provider failures into
storage-owned outbox failure inputs or invalid-token cleanup calls.

The same provider boundary validates registrations before persistence with an
FCM HTTP v1 data-only message and `validate_only: true`. The request is complete
enough that a token-specific `INVALID_ARGUMENT` is meaningful; it produces no
notification. Permanent token rejection maps to the registration API's `422`,
while auth, quota, network, and generic provider uncertainty map to `503` and
must not persist the row. Registration attestation is not part of this protocol;
a future verifier must define a typed, versioned evidence contract before the
wire format adds such a field.

Permanent token-specific FCM failures (`UNREGISTERED`, or FCM-error-detail
`INVALID_ARGUMENT`) mark the outbox row `invalid_token` and disable the
registration in one transaction, only if the current registration still
matches the snapshotted `(recipient_id, installation_id, fcm_token)` — an
old invalid token can never disable a newer registration after device-token
rotation. Generic bad-payload FCM `INVALID_ARGUMENT` failures are not token
evidence: they dead-letter the row and must not disable registrations.
Generic provider, auth, quota, network, timeout, malformed-response, or bare
`NOT_FOUND` failures are transient sanitized delivery failures and must not
disable registrations.
